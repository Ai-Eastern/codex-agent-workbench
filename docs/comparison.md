# 执行方式与旧组织链的比较

这个项目保留已有 Codex 项目和侧栏任务，把 PM、TL 之间的常规技术协调收回到 PM，并让 PM 按工作特点选择执行路线。它并不要求每次需求都组建团队。

下表中的“旧 PM–TL 链”指此前由 PM、技术负责人和工程师分层转交开发工作的组织方式。“单 Agent”和“原生子 Agent”描述执行形态；本体系仍然使用它们，并补充共同的项目知识、任务合同和验收记录。下列差异是结构对比，不是性能实验结果。

| 维度 | 旧 PM–TL 链 | 单 Agent | 直接使用原生子 Agent | 本体系 |
| --- | --- | --- | --- | --- |
| 责任 | PM 管目标，TL 拆技术和派工，工程师实现 | 一位 Agent 贯穿分析、实现和检查 | 父 Agent 拆分并接收子任务 | PM 吸收 TL 职责；工程师执行有界任务；跨项目协调者处理跨项目事项 |
| 小任务 | 容易沿用多角色转交 | 路径短，适合有界工作 | 创建和接收子任务也有成本 | `direct` 在现有 PM 任务完成，不凑人数 |
| 独立并行工作 | 由 TL 协调多位工程师 | 受当前执行者串行组织限制 | 适合独立、短期工作 | `native` 使用真实原生工具创建，先领取、再绑定实际子任务身份 |
| 依赖与接续 | 依赖角色间的计划、台账和汇报 | 由单一任务维护接续约定 | 工程级依赖和恢复规则需另行组织 | `langgraph` 保存依赖、任务状态和检查点，驱动已有桌面工程师 |
| 项目背景 | 可能在多层消息中重复转述 | 主要由当前上下文和主动读取维持 | 由父任务选取并传递 | 从项目 Markdown 检索相关片段，按任务冻结上下文及来源哈希 |
| 文件归属 | 依赖派工和角色遵守写入约定 | 单执行者时协调简单 | 父任务需要明确 disjoint write sets | 请求列出精确文件；整批预留并检查冲突，工程师只接收自己的写集 |
| 经验复用 | 取决于旧台账、文档和检索约定 | 依赖主动寻找项目文档 | 取决于父任务提供的信息 | 三条路线共用同一项目 lexical RAG；普通 Markdown 和有证据的 capture 均可检索 |
| 验收 | 多层组织可能重复复核同一结果 | Agent 自行组织检查 | 父任务接收各子任务交付 | 工程师保留必要自测，PM 入口统一执行一次独立集成验收，跨项目协调者读取摘要 |
| 失败与不确定派送 | 由旧机制和人工协调处理 | 在当前任务中诊断接续 | 父任务判断是否重新派发 | 保留原 run、attempt 和失败；不确定派送不自动重发；未解决的验收中断不自动重跑 |
| 使用成本 | 角色和交接较多 | 组织成本低 | 增加并行管理成本 | 需要项目登记、真实任务映射、合同和证据；是否值得使用由任务规模决定 |

## 为什么 PM 吸收 TL 职责

当 PM 已能确定实现范围、接口、文件所有者和验收命令，再让 TL 重述同一目标容易增加交接。当前方案让 PM 对技术方案和集成结果直接负责，工程师按明确的包执行。总经理或跨项目协调者不重复运行同一组技术验收，只处理优先级、资源冲突和需要用户决定的事项。

这个调整减少了一层常规转交，但不取消工程判断：工程师仍需要自测，PM 仍需核对实际交付，存在实质性疑问时仍需有针对性的检查。它没有把“角色更少”当成质量已经提高的证据。

## 为什么保留三条路线

- 修改一个清晰函数、配置或文档时，通常从 `direct` 开始。
- 多项工作之间没有依赖且写入文件互不重叠时，可选择 `native`；创建回执不明确时不重复创建。
- 工作存在先后依赖，或需要在已有桌面工程师任务之间持续接续时，选择 `langgraph`。

三种路线共享相同知识来源和交付标准，避免因为换执行方式就重新说明整个项目。不过，路线在请求中会被冻结；不能通过换路线、换 run ID 或换角色绕过已有失败和权限边界。

## 预期改善与验证方法

| 预期 | 实现依据 | 后续应观察的事实 |
| --- | --- | --- |
| 少重复背景 | 每任务检索并冻结相关知识，保留来源 | 背景重复说明次数、任务包大小、关键事实是否实际命中 |
| 少重复返工 | 保存有条件、有证据的经验，记录失败尝试 | 同类缺陷是否再次发生，命中的旧经验是否适用 |
| 少重复验收 | PM 统一记录集成检查，已完成且产物未变时复用结果 | 同一合同是否重复执行相同验收，失败后的处理是否保留证据 |
| 按需使用上下文 | 子任务使用自己的目标和相关知识片段 | 无关内容比例、遗漏关键条件的次数；不把它解释为自动压缩聊天 |
| 跨项目利用并行 | 各项目独立登记，由各自 PM 分流 | 实际吞吐、资源竞争、等待及冲突；当前尚无规模实测 |
| 降低陈旧证据继续被使用的机会 | 查询时重新检查显式绑定文件的哈希 | 文件变化后命中是否退出；未绑定事实仍需人工核对 |

这些是可以检验的预期，不承诺固定提速、节省 token 或降低错误的比例。更多 Agent 也可能增加调度、上下文和资源成本。实际接入范围见 [验证报告](verification.md)；后续 [三组功能对照](comparison-results.md) 包含首次失败、知识回写中断和跨组复制污染，未取得有效端到端效率结论。

单 Agent 也可以使用相同的 Skill、RAG 和验收工具；知识复用不是多 Agent 独有的优势。公平对照应保持模型、需求、知识和验收条件一致。跨项目吞吐还应与“每个项目一个独立 Agent，同时执行”比较，并分别记录耗时、模型用量、人工介入和最终质量。

## 错误与返工预计会如何变化

整体预期是交付过程更稳定、项目经验更容易延续，收益首先来自减少协调失误和重复劳动；复杂业务判断和代码正确性仍需要模型能力、需求质量与有效测试支撑。

| 错误来源 | 预计变化 | 条件与剩余风险 |
| --- | --- | --- |
| 重复派单、依赖未完成就开工、覆盖同一文件 | 有较直接的抑制作用 | 必须走控制器并遵守写集；应用层检查不限制绕过控制器的操作 |
| 重复采用已失败方案、忘记已确定约束 | 已记录且能命中的问题更容易避免 | 经验需要写清适用条件；未记录、未召回或失效的经验不提供保护 |
| 多层汇报失真、反复要求同一验收 | 预计减少 | PM 使用原始交付及持久验收记录，不能重新引入逐层全量复核 |
| 新业务逻辑、边界条件、需求歧义 | 不保证自动下降 | 正确的任务拆分和覆盖关键行为的测试仍然必要 |
| 错误知识传播、并行集成冲突 | 有新的风险 | 来源校验、按项目隔离、独占写集和集成检查减轻风险，但不证明知识每句话正确 |

短小任务相较单 Agent 的收益可能很有限；长周期、重复涉及历史决策或可分离多项目的工作更可能受益。相比旧多层链，预计等待和重复沟通减少；相比同样配备知识检索的熟练单 Agent，优势主要取决于真正可并行的工作量。这里描述的是工程预期，不是已经测得的错误率或返工率下降。

## 当前不能推出的结论

本地测试通过不能证明真实 Desktop 每个版本都兼容，也不能证明 GUI、设备、真实数据或用户验收通过。原生工具创建、桌面任务结束和结果 receipt 是需要分别核对的证据。

本体系尚未实现 OS 沙箱、semantic vectors、全自主生产运行或多项目规模验证。知识哈希检查能发现已绑定证据文件的变化，不能自动判断每句话仍然正确，更不会识别所有未写入证据的外部变化。
