## 真实执行路线

全部使用一个现有 Codex 项目中的隔离联调目录，任务实现字符串规范化、稳定去重和依赖组合；这些是联调代码，不代表该项目产品功能。

| 路线 | 实际执行 | 独立命令验收 | 结果 |
| --- | --- | --- | --- |
| `langgraph` | 现有 PM 经真实桌面 pipe 派工；工程师 A/B 就绪后派出 C | 3 条命令退出码均为 0 | `COMPLETE`；保存 1 条带证据知识 |
| `native` | PM 先领取，再真实调用原生创建工具、绑定两个子任务 | 2 条命令退出码均为 0 | `COMPLETE`；保存 1 条带证据知识 |
| `direct` | 当前 PM 直接完成单文件任务 | 1 条命令退出码为 0 | `COMPLETE`；本轮无新增知识候选 |

真实原生创建通过两次工具调用元数据、实际子任务 UUID、父 PM 标识、项目 cwd 及模型信息交叉核对；创建时 `fork_turns=none`。桌面路线分别核对登记目标、实际 cwd、新完成轮次、工程师 receipt 与命令验收，未把单个结果文件当作整个链路成功的证明。

完成后对三条路线分别再次调用 `advance`，用会立即报错的 command/desktop 回调检测任何重复动作：均返回 `reused=true`，重复命令和桌面调用均为 0，验收文件内容与时间、事件计数保持不变。

## 知识闭环与新任务检索

一条显式标注的联调约定作为初始知识。桌面和原生路线各产生一条通过验收后保存的经验。随后使用一个 `gpt-5.5/low`、`fork_turns=none` 的新任务，只给项目配置和问题，通过安装后的 Skill 检索：

- 命中联调约定、原生规范化经验、桌面组合验收经验三个知识 ID。
- 读取匹配的 Markdown 和显式绑定证据，核对文件存在、SHA-256 一致及规则内容。
- 未借助旧聊天日志，也未重跑开发或验收命令。
- 正确区分联调约定、自动化命令证据与人工验收，并指出组合知识没有直接绑定全部依赖源码。

这证明当前样例可从交付保存经验，并在新任务中重新取得有来源的上下文。它不证明所有自然语言查询的召回质量。自动捕获绑定本任务验收文件和本任务输出文件；未绑定的依赖、外部服务或业务事实变化仍需额外判断。

## 当前限制

- 当前只验证有界的单项目联调，未证明 `1-3-9`、`1-4-12` 吞吐、资源利用率或真实业务交付质量。
- 不给固定提速、降错、降返工百分比。本页首次验证时尚未开展对照；后续 [三组功能对照](comparison-results.md) 已执行，但因失败与污染没有形成有效端到端胜负结论。旧链的同条件对照仍未开展。
- Desktop pipe 是当前版本内部接口；兼容性可能随桌面版本变化。原生创建身份仍需 Codex 的真实工具证据。
- Skill 与精确写集是应用层约束，没有 OS 沙箱。暂停控制新派工，不强行终止已经执行的 Agent 或子进程。
- Markdown 可供 Obsidian 打开；本轮没有实际操作 Obsidian GUI，也未验证私人 Vault 融合。检索是词项检索，不是语义向量检索。
- 首次依赖安装跳过 native scripts 后 SQLite binding 缺失，明确执行依赖 rebuild 后已成功加载并通过测试。Skill 校验首次遇到运行时缺 PyYAML 和默认编码问题，最终在具备依赖的 Python 下以 UTF-8 完成；这些失败未计作通过。
