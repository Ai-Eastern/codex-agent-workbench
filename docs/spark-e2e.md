# Spark 完整流程测试

日期：2026-09-11。结论：**Skill → 项目知识 → 真实桌面 LangGraph 派工 → 验收 → 明确返修 → 完成已跑通，过程中有维护介入。** 最终两个业务 run 均为 COMPLETE；首次失败、原任务包和回执已保留。本轮不是无人介入成功，也不是效率对照实验。原始记录留在本机隔离测试目录；脱敏结果见 [spark-verification.json](spark-verification.json)。

## 模型与范围

测试 PM 和工程师均指定 `gpt-5.3-codex-spark/low`，未切换 5.5。只有真实额度不足才允许切换，上下文溢出、工具不支持和代码失败均不构成切换理由。早期账户查询未显示额度耗尽，后续一次用量查询不可用，不能将其解释为额度不足。

维护任务负责控制器修复、独立验收脚本和故障注入，这些工作不计为 Spark 独立完成。用户明确授权后，新建测试任务归属原 Codex 项目，保留旧任务及其历史。

业务样例是现有项目中的隔离模块：复用原 Markdown 导出逻辑，增加手机号和邮箱遮蔽预览，再用新工程师封装预览摘要。全部输入是合成数据，没有接入产品 UI、真实聊天、外部服务或私人 Obsidian Vault。只验证列明的手机号及 ASCII 邮箱规则，不宣称通用匿名化。

## 本轮修正

1. **减少重复上下文。** `status` 返回摘要，不再附完整任务包；未完成交付时 `continue` 返回待收回执信息。`start` 仍返回必要上下文，完整包通过 `packet` 显式取得。依赖原 `status.packets` 或等待态 `continue.packets` 的脚本需要调整；仓库内调用方已核对。
2. **区分两类恢复。** `retry-acceptance` 适用于产物未变且临时条件明确解除，保留有效的已通过检查。`repair-task` 在改代码前归档原失败、包及回执，保留 run/合同/文件归属，生成新 attempt，代码改变后重新执行全部原定验收。当前返修仅支持单任务 direct/langgraph，每个 run 一次；native 和依赖链返修不在支持范围。
3. **拒绝未知结果。** 超时、无确定退出码、执行中断、证据或产物漂移、锁冲突不能进入上述恢复。返修再失败后不自动循环，不更换 ID 清空预算。
4. **修正 Skill 契约。** 当前身份核对真实环境；固定文案用明确常量；自测期望对照合同，不能从实现反向复制。已安装 Skill 同步这些规则。

仓库执行 `node --test`：**34 项通过，失败 0、跳过 0**（知识 14、编排 14、恢复 6）。恢复测试先观察到缺失入口和未知退出结果保护失败，再实现修复并通过。这是控制器自动化测试数量，不是 34 个真实业务任务。

## 仍未解决或尚未证明

- 新 PM 也发生过上下文错误。已观察到大段重复工具输出，但最后一次可见输入计数低于上报的窗口上限，无法断定服务端报错的精确原因。摘要输出减少冗余，不能证明消除了上下文溢出。没有删除历史、伪造身份或替换桌面进程。
- 本轮原生子智能体工具没有 Spark 选项，因此没有进行 Spark native 实测。此前 5.5 的 native 接入证据单独保留，不能改标成 Spark。
- PM 中断后由维护者判断交接与修复；尚没有自动 PM 替换和大规模多项目故障恢复。单任务返修通过不能推导整个依赖图都能安全返修。
- 模块没有发布到产品，未做 GUI、真实数据或用户验收；应用层合同和锁不是 OS 沙箱。知识库使用词项 RAG，不是语义向量检索。
- 两段业务样例难度、上下文和维护介入不同，不能用本轮耗时计算相对旧模式的提速比例。
