# Guidance 规则按需加载结果

已采用并更新本机 Codex Skill：公共约束常驻，按工程师、PM 执行路线和恢复状态读取相关规则。借鉴 Ruflo 的 constitution + shards 设计，未导入其 npm 包、默认哈希向量或英文意图分类器。原有控制器、派工提示词、模型配置和 BM25 默认检索保持原版本。本轮没有启动恋语新功能。

这是**规则装载量优化**，尚未测得整体开发耗时或模型 Token 的下降。现有聊天已经读入的旧规则不会被清除；新版在后续读取时生效，Codex 桌面操作习惯不变。

## 实际验证与首次问题

使用三个 Luna/medium 原生子任务完成独立规则审查、工程师探针、PM 决策场景。PM 场景由验证员模拟决策，不是 Sol/high 真实项目派工，也不是与旧版随机分组的效率实验。

- 工程师实际只读取 `SKILL.md` 和 `worker.md` 两份 Workbench 规则，完成一个独占文件的合成模块。维护者按合同独立核对 10 个输入，回执身份、只读依赖及知识注入目标文件均符合要求；工具记录没有新增委派或 PM 管理调用。
- **首次并非全通过。** 工程师先写 done/自测完成回执，再执行自测；首次 Windows ESM 绝对路径导入失败，改成 file URL 后通过。原回执和首次错误保留。worker 新增“先取得真实退出码，再写成功”；单独的顺序探针实际在工具返回 `exit_code=0` 后才写新回执，没有重跑原模块的已通过检查。
- PM 首轮 10 个决策场景中，9 项关键动作判断符合冻结标准，包括 direct 当前 PM 执行、native 不重复创建、全组预检、未知送达不重发、只修知识、一次返修、暂停及统一放行。P1 错把 runtime 定位到项目/当前目录，并进行了无关目录查找；入口已明确固定到 Skill 安装目录，缺失直接 CONFIG_PENDING。
- P1 第一次定点复答虽然正确，但仍读取旧安装副本，未计作新版安装验证。更新安装副本后再次精确读取 Skill/runtime，并只检查 runtime 给出的 CLI 和 registry 路径，均存在。该项是纠正后的验证，不能记作首轮独立成功。
- 独立审查未发现阻断性规则丢失或新增人工审批；链接、原恢复正文、屏障和安装副本哈希核对通过。9 个安装文件与源码一致，原 runtime 保留，旧 Skill 已备份。

本轮不重跑未变的控制器全套验收，不声称重验了真实桌面派工、跨项目吞吐或生产恢复。已验证的是规则选择的一次工程师行为、决策问答、具体失误后的定点修正及资源安装。Skill 仍是模型指令，不能替代控制器约束或工具权限。

本轮维护还发生过补丁格式被拒绝、委派并发槽占满、探针来源文件在派发前补齐、首次日志提取只识别 function_call 而漏掉 custom_tool_call。这些执行记录保留；实际探针判定使用修正后的完整工具记录。验证成本未达到低开销结论，下一轮沿真实已授权交付采样，不再为规则改动重建整套项目试验。
