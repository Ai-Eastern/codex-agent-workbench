# 阶段交接优化：真实任务观察结果

三项改造已落地，并完成了下一项真实恋语开发：新的 CLI 支持显式输入/标注/输出路径、只校验不写入、结构化错误和输出保护。它复用上一阶段的数据生成库，6 条正例、6 条独立反例与原清单的字节哈希保持一致。正式集成验收通过，项目知识已捕获。没有训练、真实用户或生产验收。

## 哪些改变已实际发生

- 新 PM 建在原恋语桌面项目下，使用 Sol/high；阶段交接提示为 1,441 字符。旧 PM 和旧配置保留，新配置只改变 PM 身份，共用原工作目录、控制库、知识库和文件锁。
- 总经理继续 Astra/ultra，同一轮选题、创建并绑定阶段 PM。创建消息就是开发委托，没有第二轮启动、单独就绪或重复技术验收。
- PM 最后一次 `continue --output` 自动生成 delivery，包括已核对的验收、产物和知识回执。没有另外手写交付清单，没有完成后追加 status 确认。
- 本轮仍是 direct、0 工程师，按真实依赖选择路线。未为了测试安排人工并发。

## PM 前后观察

两轮均为 Sol/high，使用同一项目知识、同一控制器验收机制。上一轮实现数据转换，本轮包装并保护已有库的 CLI，工作内容不同。以下是连续真实任务的观察对照，**不是同一任务的因果提效实验或不同框架排名**。

| 指标 | 上一轮 | 本轮 |
|---|---:|---:|
| 模型响应数 | 36 | 19 |
| 每次响应平均输入 token | 208,499 | 64,955 |
| 累计原始 token | 7,539,606 | 1,250,587 |
| 非缓存输入 token | 95,915 | 88,667 |
| 输入缓存占比 | 98.72% | 92.82% |
| 输出 token | 33,643 | 16,448 |
| 收到任务至控制器放行 | 3分31秒 | 1分58秒 |
| 放行至正式验收完成 | 3分56秒 | 2分05秒 |
| 验收完成至 PM 轮次结束 | 90.2秒 | 7.3秒 |
| PM 完整轮次 | **8分57秒** | **4分11秒** |

新阶段实际观察到了较低的重复输入负担；收尾由多个整理步骤缩为保存工具生成的回执。任务内容和响应数量也有变化，不能把全部时间差都归因于上下文或 Skill。这个结果不支持“固定降低某个百分比错误率”之类结论。

## 管理成本与缓存反例

| 指标 | 上一轮 GM | 本轮 GM |
|---|---:|---:|
| 选题/交接轮次 | 2 | 1 |
| 模型响应数 | 16 | 7 |
| 轮次耗时之和 | 3分55秒 | 1分51秒 |
| 原始 token | 1,221,372 | 711,975 |
| 非缓存输入 token | 57,167 | **107,063** |

本轮 GM 包含一次新角色创建与配置绑定，不能冒充纯消息转发成本。其输入缓存占比从约 95.3% 变为 84.87%，非缓存输入增加。当前资料无法把这部分增加精确拆成设置、上下文变化或缓存行为的各自份额。

GM+PM 合计原始 token 从 **8,760,978** 变为 **1,962,562**；但非缓存输入合计从 **153,082** 变为 **195,730**，增加 **27.86%**。因此，不能把原始 token 下降 77.60% 直接宣布为费用下降 77.60%，也不能断言冷启动在每个任务上都更省。缓存属于输入，推理属于输出，未重复累加；没有订阅费率或真实扣费数据。

后续继续使用这个阶段 PM，复用交付包和项目知识；不为每个小任务重建窗口。只有长历史再次形成明显负担且存在阶段边界时，再考虑有授权的阶段轮换。
