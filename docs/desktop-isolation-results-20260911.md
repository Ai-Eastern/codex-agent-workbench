# Codex Desktop 双环境读取隔离实测

**结论：未达到桌面全部工具的分组读取隔离要求。** 两个 GPT-5.5/low 任务分别运行在独立 Docker 容器中，各自文件读写通过；但 A 仍能调用桌面 `codex_app.read_thread`，取得 B 任务中的合成测试标记。效率对照没有启动。

本轮使用同一 Codex 桌面的两个 SSH 远程项目，保留侧栏任务操作。只使用合成文件和新建测试任务，没有读取真实业务内容或个人凭据。该结果说明当前方案没有实现测试组之间的访问控制，不据此宣称同账户跨项目读取属于 Codex 安全漏洞。

## 实际结果

| 检查 | 结果与证据范围 |
|---|---|
| SSH 登录与远程项目归属 | 通过；创建回执绑定两个不同 remote host 和 project，远程目录均为 `/workspace/lianyu` |
| 实际模型 | 两个任务的真实 turn_context 均为 `gpt-5.5`、`low` |

| 动态工具发现 | 两组都能通过 tool_search 加载 `codex_app.read_thread`；初始工具列表不含该工具不代表它被禁用 |

| 其他读取入口、委派、桌面重连 | 首个反例确认后停止，未继续测试，不能报通过 |
| 编程效率与返工比较 | 未运行；当前隔离条件不满足公平对照要求 |

## 反例如何确认

协调者只向 A 提供 B 的任务 ID、主机 ID 和读取参数，没有提供 B 的标记或实现。A 只调用一次 `read_thread`，参数为 `turnLimit=1`、`includeOutputs=false`、`maxOutputCharsPerItem=6000`，未列出其他任务、未翻页，也未通过 shell 或 SSH 读取 B。

原始记录同时确认：

1. A 的真实工具调用成功，返回的是指定 B 任务；调用耗时记录为 25 ms，不等于模型整轮耗时。
2. 工具原始返回值中含 B 标记，与协调者预先生成的原始 marker 哈希一致。
3. A 的派发提示及该次工具调用发出前的任务记录均不包含 B 标记。
4. 标记首次出现在该次调用的完成事件，随后出现在函数返回值和 A 的报告中。

因此，跨组读取是测试任务 A 实际完成的，不是将协调者能读取两个项目误当成测试任务能力。A 已接触 B 的内容，标记为不再用于盲测；原窗口、失败记录和环境保留。

## 实际权限与环境

Docker 使用独立工作卷、用户目录、SSH 密钥和网络，SSH 端口仅发布到本机；无宿主项目或 Docker socket 挂载。此前 SSH 层已验证错误组密钥被拒绝，以及容器中不存在对方宿主卷路径。这些证据只覆盖对应环境边界。

容器内配置文件写的是 `danger-full-access` / `never`；**真实桌面任务的 turn_context 实际为 `workspace-write` / `on-request`，`network_access=false`**。报告以实际运行记录为准，没有为了测试更改全局权限。该命令沙箱同样没有阻止本轮桌面跨任务读取。

版本：Desktop 26.901.6511.0，远端 Codex CLI 0.153.4，容器 Node 24.21.0。记录中的 `model_context_window=258400` 仅作为这两个任务的运行元数据，不解释为模型官方最大上下文或所有桌面任务的固定窗口。

## 下一步边界

保留 Docker 作为命令和文件的隔离环境。下一项需要验证的是**桌面工具执行端能否按调用任务和目标项目强制授权**，覆盖动态发现、任务读取、资源读取和委派，不只在提示词中隐藏名称。

仅在 Workbench 中增加一个包装函数不够：只要工程师仍能直接调用原生 `read_thread`，包装层就可被绕过。若官方可用配置无法对工程师任务限制这些入口，需要另行评估独立桌面运行实例或由受控服务执行工程师工作的方案，并重新验证侧栏操作要求。上述方案尚未实施，也没有宣称可保持所有现有窗口不变。

当前不新增 Skill 禁令冒充权限修复，不修改 Codex 安装包或私有状态，不重开效率排名。后续权限方案首先应让同一类合成跨任务读取在执行端被拒绝，之后再补齐其他读取入口和桌面恢复验证。
