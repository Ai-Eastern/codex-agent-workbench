# 三项目调度、RAG 与成本结果（2026-09-12）

双项目 1-2-6 已通过。加入 HiveMind 后，三个项目的编码合同经过一次定点返修全部通过；随后统一放行的知识交付观测到真实 9 人并发，并完成 9 条 Obsidian 知识的写入与重新检索。当前可以由一个总经理协调三个 PM，每项目按任务使用 0–3 名工程师。这里证明的是有界调度和知识闭环；尚不能宣称九人生产编码更快、更省或返工率下降某个比例。

## 实际任务与结果

PM 使用 gpt-5.6-sol/high，工程师使用 gpt-5.6-luna/medium；保持既有 Codex Desktop 项目侧栏。工程师由真实 PM 的控制器派送，保留真实任务、轮次、合同、产物与验收哈希。

| 阶段 | 实际结果 | 工程师峰值 | 全员重叠 |
|---|---|---:|---:|
| 原 1-2-6 | 恋语 27 项检查通过；另一项目首条派送回执异常，三位工程师未执行 | 3 | 未形成六人并行 |
| 优化后的 1-2-6 | 两项目 COMPLETE，45 项检查通过 | 6 | 12.966 秒 |
| 三项目编码 | 恋语 21、Agent协同 21、HiveMind 25，共 67 项检查通过；HiveMind C 一次明确返修 | 6 | 未形成九人重叠 |
| 三项目知识交付 | 三项目各 3 张独立知识卡通过新合同；原编码检查重跑 0 次 | 9 | 22.529 秒 |

第一阶段归档状态未在预检中识别，旧 notLoaded 与历史 completed 被误认为可用。已补齐明确未归档、项目目录和真实完成基线校验。原回执拒绝的底层详细原因当时没有保存，不能断言归档就是运输层拒绝的唯一原因。原失败 run/attempt 保留，满足未送达证据后受控接续；未另建 run 绕过。

优化后的恋语任务复用已经通过的前置模块，另一项目恢复原合同，任务量与原批次不相同。三项目编码阶段虽然全部派出，PM 启动时间差使峰值只有六人。因此增加有期限 ready/release，让各 PM 在同一轮登记就绪、统一放行；九人并发发生在后续真实知识交付中，没有给工程师添加等待来伪造重叠。

HiveMind C 曾把非数组 dependsOn 继续调用 some，提交 BLOCKED。保留首次回执与代码，只为 C 生成一次新 attempt；A/B 与其他两项目没有重派。各完成项目的最终集成均为控制器单次执行；67 项是返修后的结果，不是首次全部通过。

## RAG 实质结果

三项目共 9 条知识由工程师正常交付中的 knowledgeCandidate 提供，经集成通过后自动写入各自获授权的 Obsidian 项目目录。新建检索实例后按期望 ID 与接口关键词逐条查询，9/9 命中，同时核对笔记哈希、示例文字与旧模块 SHA-256。全部项目状态 COMPLETE，没有待补知识候选。

这批记录是已验收的合成合同案例。自动 capture 绑定知识卡和验收证据；旧模块哈希写在卡片内，本轮另行核对。它不等于任何产品源文件改变都会自动让笔记失效。正式产品使用前仍需核对适用版本。

按 task.knowledge 限定 ID、查询和正文预算，ID 过滤在排名/limit 之前执行；空 ID 集合不会退回其他知识。本批每包知识正文为恋语 555 字符、另两项目各 112 字符。这只是检索正文，不包括提示协议、来源头、合同和旧聊天历史，也不是 Token 数。当前为 FTS5/BM25 词项检索，没有 embedding 或无 RAG 消融实验，不能给出 RAG 降错比例。

本轮按明确 turn_id 对 token_usage_record 的 response_id 去重，逐次 usage 加总，与最后的 turn_token_usage 对账；上述 PM/工程师轮次均完整、对账通过。原累计 token_count 在部分长期会话中出现 counter_reset，曾只能得到 1-2-6 工程师 2,853,461 的下界；新归因记录核对后完整值为 3,142,644。旧报告不覆盖、不把下界伪装为完整成本。

各阶段从第一名角色本轮开始到最后一名结束分别为 195.496 秒、595.859 秒、152.731 秒；第二项包含 C 返修与中间等待。它们不是从用户最初授权开始的总交付耗时。框架开发、合同准备、根协调、审查、脚本修正、角色初始化和 Ruflo 调研另列于 [维护与调研消耗](dispatch-support-cost-20260912.md)，不能当作零。现有 PM 长对话带来大量重复缓存输入；只有减少实际交接与无关上下文，才可能改善下一批成本。

## 与原有方式的比较

| 对象 | 已有证据 | 可以得出的结论 |
|---|---|---|
| 旧 PM→TL→工程师链 | 本轮改为 PM 兼技术职责，取消同结果的总经理重复验收 | 角色层级和重复验收入口减少；不能还原旧两小时阻塞的全部原因 |
| 单 Agent | 旧同模型 Spark direct 首验失败，705.520 秒，2,649,839 total | 有真实成本记录，但失败样本不能用来断言团队成功交付更快 |
| 固定前后端/测试等团队 | 旧 Spark 固定组工程通过、知识未闭环，153.451 秒，3,014,919 total；9 次额外验收尝试中 6 次失败 | 专业能力仍需要；当前改进在按依赖用人和复用验收，不在岗位名称 |
| 旧动态组 | 复制固定组 7 个实现文件，判 INVALID | 从效率排名中排除，保留污染证据 |
| 原生子 Agent vs LangGraph | 5.5 pilot 第一批 native 通过、graph 失败且合同不等；第二批合同对等但双方失败 | native 工程师消耗 725,527 / 663,560，graph 1,024,698 / 904,493；不能作成功交付优势归因 |
| 当前三项目 | 真实项目路由、独占写集、统一放行、定点恢复、一次集成、9 条知识回写检索有证据 | 适合开始有具体业务目标的三项目协同；不是无人介入保证 |

RAG、持久状态和验收记录固定岗位团队同样可以使用。后续真正值得比较的是相同模型、需求、初始代码、知识、验收和资源预算下的合格交付时间、全角色 Token、返工次数及人工介入；知识交付和编码任务分开统计。尚未完成工具层全面读取隔离，不能把旧污染对照继续用于排名。

## 发布与接续

Skill、RAG 引擎和 LangGraph 控制器在同一个私有仓库发布；真实项目配置、角色任务 ID、完整日志、Vault 正文和个人文件留在本机。PM 按任务选择 direct/native/langgraph，不默认开满三名工程师；总经理处理项目间目标和冲突，不新增技术负责人层。

九人实测后，发布前审查发现迟到原消息可能重派、完成项缺少原始产物哈希两个恢复边界，以及 CLI 相对 barrier 路径不一致。修复与验证细节见 [本轮维护记录](dispatch-support-cost-20260912.md)。这些边界由聚焦回归验证，不重跑已完成的业务批次；上述实测不冒称修复后代码的全量桌面重测。

Ruflo 作为独立只读调研完成，未安装或替换当前框架，见 [适配评估](ruflo-assessment-20260912.md)。当前进入真实业务使用后的持续评测，不继续扩大 Docker 隔离或合成并发测试。
