# 恋语真实开发：Ruflo 复用与成本定位

本轮完成了实际数据工程交付，也把 Ruflo 的纯快照比较逻辑用到了真实 Codex 日志。观察到的主要成本驱动是长上下文重复输入、管理准备与收尾，以及此次全量调查和框架改造。现有轻量检索/控制器的单次工具往返在一秒以内。本轮走 direct，没有测量 1-3-9 的工程师桌面派工延迟，不能将这个结论外推为所有 LangGraph 批次的结论。

## 实际交付

总经理选择现有恋语策略数据的下一项真实任务，真实 PM 使用 **Sol/high、direct、0 名工程师**，沿正式项目控制器完成：

- 6 条正例 SFT 种子、6 条独立反例审阅记录、显式目标回复方/轮次标注、来源 SHA-256 清单。
- 本地导出与校验入口，不静默过滤无效数据，不把反例写入正例目标；B2-T3 明确绑定目标回复方，不能用最后一句替代。
- 同一个正式集成验收命令通过，覆盖来源与标注、确定性字节输出、正反例隔离、来源追溯、指定目标绑定、错误输入拒绝六组检查。
- 控制器状态 COMPLETE，验收命令耗时 84ms；知识候选已捕获到恋语的 Obsidian 项目知识目录。总经理没有重复执行技术验收。

这是首批种子数据转换与本地验收交付，`trained=false`、`humanVerified=false`，没有宣称足量训练集、模型质量提升或训练器兼容实测。原始素材未改写。

## 时间花在哪里

| 观测区间 | 时间 | 口径 |
|---|---:|---|
| GM 选题轮 | 2分53秒 | 完整轮次，和部分源码调查并行 |
| GM 交接轮 | 1分01秒 | 包括阅读计划、发送及保存回执；不是传输延迟 |
| PM 收任务 → 控制器 RUNNING | 3分31秒 | 规则/材料读取、检索、计划与合同等组合准备 |
| 控制器 RUNNING → 验收完成 | 3分56秒 | 实施、自检、提交结果及正式验收 |
| 验收完成 → PM 轮次结束 | 1分30秒 | 知识与交付记录、状态确认和最终回复等收尾 |
| PM 完整轮次 | **8分57秒** | 上述三个 PM 区间的总和 |

相关顶层工具往返：search **683ms**、prepare **714ms**、start **693ms**、continue **843ms**。这是包住对应命令的 `exec` 往返，含工具封装，不能冒充纯 LangGraph CPU 时间。正式 acceptance 事件至 COMPLETE 的间隔约 **48ms**；不将其单独当作完整 RAG 写入耗时，因为其内可能包含状态持久化等工作。

本次 `cost-report` 对 6 份明确授权的 rollout、10 个 actor-turn 范围采集一次，包含 Node 启动、CLI 导入、解析、汇总、写出，共 **669ms**。没有 npx、后台常驻服务或为了采集成本再开一个模型任务。

PM 准备约占该轮 **39.3%**，验收后收尾约 **16.8%**。两者包含有价值的检查和知识保存；这些时间可以作为下一轮优化目标，不能全部视为浪费。没有逐阶段的精确 token 归因，阶段时间也不能直接解释为模型计算时间。

## 实际用了 Ruflo 哪部分

完整判断见 [成本模块评估](ruflo-cost-assessment-20260912.md)。本地 `cost-diff` 已对交付结束前、结束后两个真实快照执行差异比较：已观测总量增加 **3,360,063 token**。因为两个快照包含尚未结束的维护轮，总量比较保持 `complete=false`，仅展示 `observedLowerBoundDelta`，没有将 **17.07% 的区间增长**包装成性能退化或提效比例。

这项实操验证的是：纯比较算法可以改造复用；Codex 的明确响应归因可以去重并与轮次累计核对；不完整数据不会假装完整。没有安装 Ruflo 整个成本插件，没有采用 Claude 价格表、自动硬停或降级模型。

## 下一步应改什么

1. **优先治理角色上下文。** 按已验收阶段保存短交付包，下一独立阶段仅携带目标、当前代码入口、必要决策和检索证据。保持现有桌面项目与角色使用方式；如果需要轮换任务，以可追溯交接实施，不假设 RAG 能清除已有聊天历史。本轮尚未测量轮换后的节省量。
2. **合并小任务的选题与发送。** 这次为了并行准备成本接入，GM 拆成选题和交接两轮；常规任务已有明确目标时应一次转派，减少重复阅读计划和回执整理。总经理继续只读 PM 摘要。
3. **缩短收尾和工具回显。** 复用控制器的一份 acceptance、知识回执和产物清单，减少另外生成内容相近的长报告；只给必要摘要和路径，避免大段日志反复进入上下文。
4. **下一次对真实可拆分任务做对照。** 沿用这个本地采集器，同模型、相近任务复杂度、相同知识与验收口径，对比当前方式和缩短上下文/合并交接后的方式。需要并发才选择 native 或 LangGraph，不为展示架构安排空工程师。

这些优化目标来自本轮证据；它们尚不是已实现的节省承诺。此处不继续启动新一轮业务或人工并发基准。
